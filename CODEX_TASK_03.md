# Codex Task 03 - проверка, закрытие и лист сборки

Работай в этом репозитории. Главный источник требований - `SPEC.md`.

Первые два этапа завершены: XLSX импортируется в PostgreSQL, заказ распределяется между сборщиками, позиции проходят складской процесс, а действия сохраняются в журнале.

Цель задачи: довести заказ от завершения сборки до проверенного и закрытого состояния и сформировать итоговые документы.

## Сделать

1. Реализовать управляемую проверку проблемных позиций заказа со статусами `NOT_FOUND`, `SKIPPED` и типом отбора `REVIEW`.
2. Разрешить администратору до закрытия заказа изменить тип отбора проблемной позиции на `PACKAGE` или `PIECE` с корректным количеством и обязательным комментарием.
3. Добавить административное решение по `NOT_FOUND` и `SKIPPED`: подтвердить проблему либо вернуть позицию в работу с назначением доступному сборщику.
4. Все решения проверки выполнять транзакционно и сохранять отдельными неизменяемыми событиями журнала с пользователем, комментарием и предыдущими/новыми значениями.
5. Добавить явное закрытие заказа `COMPLETED/REVIEW_REQUIRED -> CLOSED`. Запрещать закрытие, пока остаются нерешённые проблемные позиции или позиции без финального статуса.
6. При закрытии заполнять `closedAt`, освобождать занятых этим заказом сборщиков и записывать событие закрытия.
7. Добавить API сводки проблем по всем открытым заказам с фильтрами по заказу, типу проблемы и статусу решения.
8. Добавить API истории заказов с поиском по номеру документа и фильтрами по статусу и датам.
9. Добавить API для получения журнала событий с пагинацией и фильтрами по типу события, сборщику и позиции.
10. Реализовать в веб-терминале отдельные разделы `Проблемы` и `История`, сохранив существующую визуальную систему.
11. В разделе `Проблемы` показывать товар, штрихкод, тип/количество отбора, сборщика, причину, время и доступные действия проверки.
12. В карточке заказа показывать временную шкалу событий, итоговую статистику, кнопку закрытия и понятные причины, если закрытие недоступно.
13. После завершения или закрытия заказа формировать короткий печатный PDF A4 `Лист сборки`.
14. Формировать полный электронный PDF-отчёт со всеми товарами, штрихкодами, количеством и типом `УПАК/ШТ`, сборщиком, финальным статусом и временем подтверждения.
15. В оба PDF включать номер и дату документа, склад, начало/конец/общее время, всего/собрано/не найдено/пропущено, статистику сборщиков, блок проблем, поле `Проверил` и QR-код/ссылку на заказ.
16. Генерировать PDF на сервере из данных PostgreSQL без доверия к данным клиента. Отдавать корректный `application/pdf` и безопасное имя файла.
17. Добавить кнопки скачивания короткой и полной формы в карточку заказа; для незавершённого заказа показывать понятную ошибку.
18. Обновить Prisma-схему, миграции, seed и README для нового процесса проверки, закрытия и отчётности.

## Рекомендуемый API

- `GET /api/problems`
- `PATCH /api/order-items/:id/review`
- `POST /api/order-items/:id/resolve-problem`
- `POST /api/orders/:id/close`
- `GET /api/orders/history`
- `GET /api/orders/:id/events`
- `GET /api/orders/:id/reports/short.pdf`
- `GET /api/orders/:id/reports/full.pdf`

Названия маршрутов можно скорректировать, если итоговый API остаётся последовательным и документированным.

## Автотесты

1. Проверка запрета закрытия заказа с незавершёнными или нерешёнными проблемными позициями.
2. Проверка корректного закрытия заказа, заполнения `closedAt`, освобождения сборщиков и записи события.
3. Проверка изменения `REVIEW` на `PACKAGE/PIECE`, валидации количества и обязательного комментария.
4. Проверка подтверждения проблемы и возврата позиции в работу.
5. Проверка фильтрации проблем, истории и пагинации событий.
6. Интеграционный сценарий для тестового XLSX: импорт 48 позиций, назначение, завершение с одной проблемой, решение, закрытие.
7. Проверка обеих PDF-форм: HTTP-заголовки, валидный PDF, номер заказа, 48 товарных строк и обязательные разделы.
8. Регрессия: повторный импорт не создаёт дубль, распределение и переходы статусов второго этапа продолжают работать.

## Критерии приёмки

- Заказ нельзя закрыть до завершения сборки и решения всех проблем.
- После решения проблем заказ закрывается и получает `closedAt`.
- Закрытый заказ доступен в разделе `История` и имеет полный журнал действий.
- Раздел `Проблемы` показывает только актуальные проблемы и позволяет безопасно принять решение.
- Короткий PDF помещает оперативную сводку и проблемные позиции в печатную форму A4.
- Полный PDF содержит все 48 позиций тестового заказа и статистику каждого сборщика.
- QR-код ведёт на карточку соответствующего заказа.
- API не раскрывает `passwordHash` и не принимает итоговые цифры отчёта от клиента.
- Миграции применяются на чистой PostgreSQL без ручных изменений.
- `npm test`, `npm run lint` и `npm run build` проходят.

## Требования к качеству

- Бизнес-логику проверки, закрытия и построения отчёта вынести из HTTP-обработчиков в тестируемые модули.
- Не изменять и не удалять старые события журнала; каждое административное решение добавляет новое событие.
- Сервер самостоятельно вычисляет возможность закрытия и статистику отчёта.
- PDF должен корректно отображать кириллицу и не обрезать длинные наименования товаров.
- Ошибки API должны быть понятными на русском языке и иметь корректный HTTP-статус.
- Сохранять обратную совместимость импорта, распределения и существующего API.

В конце самостоятельно запусти PostgreSQL и приложение, выполни миграции, импортируй тестовый XLSX, пройди сценарий с проблемной позицией и закрытием, скачай и проверь обе PDF-формы, затем запусти тесты, линтер и сборку. Исправляй ошибки до полного прохождения проверок.
