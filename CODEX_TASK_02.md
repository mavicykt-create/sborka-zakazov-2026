# Codex Task 02 — сборщики и распределение заказа

Работай в этом репозитории. Главный источник требований — `SPEC.md`.

Первый этап уже завершён: XLSX импортируется, заказ сохраняется в PostgreSQL и показывается в главном веб-терминале.

Цель задачи: добавить управляемый складской процесс от назначения сборщиков до фиксации результата по каждой позиции.

## Сделать

1. Расширить Prisma-схему сущностями сборщика, назначения позиции и журнала событий.
2. Для сборщика хранить уникальный логин, хэш пароля, имя, активность и статус смены `OFF_SHIFT / AVAILABLE / BUSY`.
3. Пароль никогда не хранить и не возвращать в открытом виде. Для создания и смены пароля использовать надёжный password hash.
4. Добавить API главного терминала для списка, создания и изменения сборщиков, включая включение/выключение и статус смены.
5. Добавить назначение заказа на выбранных активных сборщиков. Одна товарная строка целиком принадлежит одному сборщику.
6. Распределять позиции максимально равномерно: разница в числе назначенных строк между сборщиками не более 1. Порядок должен быть детерминированным.
7. Запрещать назначение неактивным сборщикам и сборщикам `OFF_SHIFT`. Возвращать понятные ошибки валидации.
8. После назначения переводить позиции `PENDING -> ASSIGNED`, заказ `NEW/READY -> ASSIGNED`, выбранных сборщиков — в `BUSY`.
9. Реализовать безопасные переходы позиции: `ASSIGNED -> ACTIVE -> PICKED | NOT_FOUND | SKIPPED`. Не разрешать недопустимые переходы.
10. При начале первой позиции переводить заказ в `PICKING` и заполнять `startedAt`.
11. Когда все позиции имеют финальный статус, переводить заказ в `COMPLETED` либо `REVIEW_REQUIRED`, если есть `NOT_FOUND`, `SKIPPED` или позиции типа `REVIEW`. Заполнять `completedAt`.
12. Сохранять неизменяемый журнал событий: назначение, начало сборки, `PICKED`, `NOT_FOUND`, `SKIPPED`, отмена допустимого последнего действия, передача позиции другому сборщику и завершение.
13. У события хранить время сервера, необязательное время устройства, пользователя/сборщика, заказ, позицию, тип и JSON metadata.
14. Добавить API получения журнала заказа и перераспределения только незавершённых позиций.
15. Расширить `GET /api/orders/:id`: возвращать назначенного сборщика, прогресс и сводку по статусам без раскрытия `passwordHash`.
16. Расширить React/Vite терминал разделом «Сборщики», карточками смены и формой назначения выбранных доступных сборщиков на заказ.
17. В карточке заказа показывать прогресс, назначенного сборщика и статус каждой позиции. Добавить безопасные кнопки для симуляции переходов статуса без Android.
18. Добавить блок «Требует внимания» для `NOT_FOUND`, `SKIPPED`, `REVIEW` и ошибок назначения.
19. Подготовить Prisma-миграцию и тестовые данные минимум для трёх сборщиков без настоящих паролей в репозитории.
20. Обновить README: миграции, создание сборщиков, назначение заказа и проверка рабочего сценария.

## Рекомендуемый API

- `GET /api/workers`
- `POST /api/workers`
- `PATCH /api/workers/:id`
- `POST /api/orders/:id/assign`
- `POST /api/orders/:id/reassign`
- `PATCH /api/order-items/:id/status`
- `POST /api/order-items/:id/undo`
- `GET /api/orders/:id/events`

Названия маршрутов можно скорректировать, если итоговый API остаётся последовательным и документированным.

## Автотесты

1. Unit-тест алгоритма распределения для 48 позиций между 2, 3 и 5 сборщиками.
2. Проверка, что разница распределения не превышает 1 и ни одна позиция не потеряна и не назначена дважды.
3. Проверка отказа для неактивного сборщика и `OFF_SHIFT`.
4. Проверка допустимых и недопустимых переходов статусов позиции.
5. Интеграционный тест: импорт тестового XLSX, создание трёх сборщиков, назначение 48 позиций как `16/16/16`.
6. Проверка завершения заказа и наличия событий в журнале.
7. Проверка, что API никогда не возвращает `passwordHash`.

## Критерии приёмки

- `test-data/sample-order-12293.xlsx` по-прежнему импортируется как заказ на 48 позиций.
- Три доступных сборщика получают по 16 товарных строк.
- Для двух сборщиков распределение составляет `24/24`, для пяти — `10/10/10/9/9` в детерминированном порядке.
- В терминале видны сборщики, их смены, назначение и прогресс заказа.
- Проблемные позиции попадают в блок «Требует внимания».
- Каждое изменение статуса и назначения отражается в журнале.
- Повторный импорт XLSX по-прежнему не создаёт дубль.
- Миграции применяются на чистой PostgreSQL без ручных изменений.
- `npm test`, `npm run lint` и `npm run build` проходят.

## Не делать пока

- аналитику производительности.

## Требования к качеству

- Бизнес-логику распределения и переходов статусов вынести из HTTP-обработчиков в отдельные тестируемые модули.
- Операции назначения, изменения статуса и записи события выполнять транзакционно.
- Не удалять события журнала при отмене; отмену записывать отдельным событием.
- Не доверять идентификаторам и статусам из клиента без серверной проверки.
- Сохранять обратную совместимость импорта и существующих API первого этапа.
- Ошибки API должны быть понятными на русском языке и иметь корректный HTTP-статус.

В конце самостоятельно запусти PostgreSQL и приложение, выполни миграции, импортируй тестовый XLSX, пройди сценарий назначения и завершения заказа, затем запусти тесты, линтер и сборку. Исправляй ошибки до полного прохождения проверок.
